# Как контрибьютить

Проект пет-овский, но правила дисциплинируют и защищают от регрессий.

## Ветки

- `main` — стабильная ветка; сюда попадает только то, что собирается и проходит тесты.
- Рабочие ветки — короткоживущие, от `main`: `feat/…`, `fix/…`, `docs/…`, `chore/…`.
- Имена: `feat/sacks-layout`, `fix/preset-load-crash`, `docs/roadmap-m1`. Нижний регистр, дефисы, без имён и дат.
- Ветка живёт один PR; после вливания удаляется, чтобы не копить мёртвые ссылки.
- Перед PR рабочий бранч ребейзим на актуальный `main`; прямые merge-коммиты из `main` в ветку не делаем.
- Прямые коммиты в `main` допустимы только для тривиальных правок (опечатка, README); всё остальное — через ветку и PR.
- Историческая ветка прототипа `vibe-coding` влита в `main` в M0; новую работу вести от `main`.

## Коммиты

Стиль репозитория — короткое повелительное наклонение, английский, без префиксов:

```text
Improve formula for point size
Extract saving a file
Add Sacks layout
Fix preset round-trip for missing palette
```

Правила:

- один коммит — одно логическое изменение;
- заголовок до 72 символов, без точки в конце, без `WIP`;
- тело пишем только когда нужно объяснить «почему»: пустая строка после заголовка, затем 1–3 строки; «что» и так видно в diff;
- ссылка на issue — в теле: `Refs: #12`;
- незаконченную работу держим локально или в черновом PR, а не в виде `WIP`-коммитов в `main`;
- не коммитить сгенерированные артефакты (`*.png`-превью, `bin/`, `obj/`);
- не коммитить секреты и локальные пути.

## Вливание

- Рабочая ветка вливается в `main` через squash-merge: один PR — один коммит в истории.
- Merge-коммиты не используем, история `main` линейная.
- Ветка вливается только после зелёных `dotnet build` и `dotnet test` из PR-чеклиста ниже.
- После вливания ветка удаляется.

## Служебные файлы

- `.kilo/` — локальное состояние агента (планы, worktrees, `agent-manager.json`); в Git не попадает и перечислена в `.gitignore`.
- `.vscode/` — в Git только общие `settings.json`/`tasks.json`/`launch.json`/`extensions.json`; личные настройки остаются локально.
- Сгенерированные превью (`temp_preview.png`, `plot*.png`) в репозиторий не добавляем.

## Pull request

Чек-лист перед PR:

- [ ] `dotnet build` и `dotnet test` зелёные;
- [ ] изменение покрыто тестом там, где это возможно без графики;
- [ ] документация обновлена в том же PR: roadmap/use-cases при продуктовых изменениях, ADR при архитектурных, guides при изменении команд;
- [ ] нет молчаливых `catch` и проглоченных ошибок;
- [ ] нет новых временных файлов и хардкода путей;
- [ ] имена и комментарии не дублируют код; комментарии объясняют «почему», а не «что».

## Код-стайл

- Язык идентификаторов и текстов коммитов — английский; документация — русский, README двуязычный.
- `Nullable` включён; предупреждения сборки не игнорируются.
- File-scoped namespaces, один публичный тип на файл.
- Ядро без внешних зависимостей; `Core` не ссылается на WPF/Skia.
- Никакой математики в UI-слое: всё через `Core`.
- Горячие циклы — без LINQ и лишних аллокаций.
- Не добавлять комментарии, объясняющие очевидное; сложные формулы — со ссылкой на [04-math](../04-math/layouts.md).

## Изменение планов

- Roadmap и vision меняются только отдельным PR с явным описанием «почему».
- Архитектурное решение фиксируется ADR до реализации, а не после.
- Отложенная идея попадает в [non-goals.md](../01-product/non-goals.md#отложенные-идеи), а не в код «на будущее».

## Definition of Done

1. Код собирается и работает по критериям приёмки из [use-cases.md](../01-product/use-cases.md).
2. Тесты написаны и зелёные.
3. Документация отражает фактическое поведение.
4. В репозитории нет временных артефактов и отладочного мусора.
